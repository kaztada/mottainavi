# 自治体を追加する

もったいナビに自治体を1つ追加するときの、最初から最後までの手順。優先順位は **誤案内ゼロ > 月額0円 > 1人で維持できること > 対応自治体数**。怪しいデータは入れない。

Kaz が決めるのは2か所だけ: **入れるか保留か**(手順3)と **本番へのマージ**(手順6)。それ以外は止まらずに進める。Kaz はエンジニアではないので、報告は専門用語を避け、何が起きるかを平易な日本語で書く。

始める前に、記憶ファイル(nationwide-expansion-plan / release-via-pr / dev-pipeline)と `docs/roadmap.md` の Phase C を読み、その自治体が過去に調査済み・保留になっていないか確かめる。

## 1. 調査: データとライセンス

**候補から探すとき**(自治体名の指定が無い場合): BODIK のカタログ API(`https://data.bodik.jp/api/3/action/package_search?q=ごみの分別方法&rows=200`。「分別」でも検索)で、ライセンスと更新日つきの一覧が取れる。CSV を開いて、列名が「…分別方法_品目」なら標準形式。記憶ファイル nationwide-expansion-plan に 2026-10-02 時点の候補一覧がある。

確かめること(すべて市の一次情報で。まとめサイトは使わない):

- **品目別の分別一覧がどこにあるか、形式は何か**。探す順: 市のオープンデータのページ → BODIK などのデータカタログ → 市のごみのページ(PDF・Excel・HTML 表)。検索語は「〇〇市 ごみ 分別 オープンデータ」「ごみの分別方法 CSV」
- **ライセンス**。利用規約の原文まで開いて確認する。CC BY・政府標準利用規約なら使える。サイト全体が「無断転載禁止」でデータに個別のライセンスが無い場合(堺市がこれ)、検索システムやアプリ(ごみサク・さんあ〜る)にしか無い場合は **使えない**。**不明なら入れない**
- **出典表記の指定**。規約に書式があればそのとおりに書く(平塚市・河内長野市は「このデータベースは以下の著作物を改変して利用しています。…」)
- **データの更新日**。掲載ページの更新日ではなく、データ自体の基準日(泉大津市はページが2023年更新でも中身は2016年だった)
- **粗大ごみの出し方**。事前申込制か、申込先(電話・ネット)、手数料の決め方。市の申込みページで確認する
- **CSV の全部の列**。「注意点」のほかに「備考」「料金備考」などの列に出し方の注意が入っていないか(鹿児島市は備考列に粗大ごみの申込先があった)。入っていれば `extraNoteColumns` で注意文言に足す

守ること: 市のサイトへの取得はファイルごとに1回。scratchpad に保存して使い回す。この Mac の python3 は HTTPS が失敗するので、取得は curl で行う。

## 2. 照合: データが古くなっていないか

オープンデータは、市が出し方を変えたあとも更新されていないことがある(寝屋川市・泉大津市)。入れる前に、市の現行の案内と突き合わせる。

- **ごみサクがある市**(「ごみサク 〇〇市」で検索。`https://www.gomisaku.jp/<4桁>/`):
  `npm run compare-gomisaku -- --code <4桁> --csv <CSVのパス>` で全件を照合する。「食い違いの候補」と「個別に確認する品目」を読む
- **ごみサクが無い市**(ごみサクの対応自治体と4桁のコードは gomisaku.jp のトップページの一覧で分かる。さんあ〜るの市には無い): 市の現行の冊子(PDF)・ページと突き合わせる。PDF から文字が取り出せるなら、「品目名 … 区分名」の行を拾って CSV と品目名で機械的に照合する(鹿児島市は900品目を照合できた)。食い違いの候補は、PDF のページ画像と市の区分別のページで1件ずつ確かめる。文字が取り出せない・崩れるときは、ページを画像にして、危険物の全品目+粗大ごみ+無作為の20品目以上を目で突き合わせる
- **食い違いが出たら、どちらが新しいかを別の市の資料で確かめる**。ごみサクのほうが古いこともある(平塚市では電話番号と3品目が古かった)
- **必ず個別に見る品目**: 充電式電池・モバイルバッテリー・ボタン電池・スプレー缶・カセットボンベ・ライター・蛍光灯・LED・水銀製品・パソコン・消火器。ここの誤案内は火災につながる

## 3. 判断材料を出して、Kaz に決めてもらう(関所1)

次の内容を短くまとめて示し、AskUserQuestion で「入れる/保留」を選んでもらう。おすすめを先頭にする。

- 品目数、形式、ライセンス、データの更新日
- 照合の結果: 何品目を照合して、何品目が食い違ったか。食い違いの中身(表にする)
- 危険物の扱いに食い違いがあるか
- おすすめとその理由

目安: 危険物の区分が現行と違う、または食い違いが多い(寝屋川市は17品目中2品目)なら **保留** をすすめ、市にデータの更新を依頼する候補として記録する。数品目だけ手で直して入れる方法は、出典があいまいになり、維持もできないのですすめない。

危険物ではない品目が1〜2件だけ食い違う場合(鹿児島市の「化粧品の容器<プラ製>」)は、入れたうえで `itemNotes` を使う: 市のデータは書き換えず、その品目の注意文言の先頭に「※もったいナビ注: 市のページでは「〇〇」と案内されています。…最新は公式サイトでご確認ください。」と添える。この扱いも判断材料に書いて Kaz に示す。

保留になったら、`docs/roadmap.md` の Phase C の表と記憶ファイルに理由を記録し、PR を出して終わる。

## 4. 実装

CLAUDE.md の「プラン → 承認 → 実装」に従い、プランモードで計画を出してから実装する。

### 国の標準形式の CSV(列名が「ごみの分別方法_品目」「ゴミの分別方法_分別区分」など)

共通アダプタ(`scripts/core/standard-csv.ts`)を使う。書くのは設定とデータだけ。手本は `scripts/adapters/hiratsuka-city/index.ts` と `scripts/adapters/higashiosaka-city/index.ts`。

1. `scripts/adapters/<slug>/index.ts` — `StandardCsvConfig`(取得元、文字コード、列名の接頭辞、区分の表記 → 区分ID、公式リンク、収集しない区分、区分の説明)
2. `scripts/adapters/index.ts` に1行追加
3. `data/municipalities/<slug>/categories.json`、`municipality.json`、`reuse-overrides.json`(最初は `{}`)
4. `data/municipalities.json` の該当行を `supported` にし、`official_url` を入れる
5. `data/reuse-options.json` に市の小型家電回収ボックス(`municipality_id` 付き。市の案内ページで設置場所を確認)

slug はレジストリ(`data/municipalities.json`)にあるものを使い、変えない。`item_id_prefix` は既存と重ならない英小文字3字。`data_version` は作業日(yyyymmdd)。

### それ以外の形式

個別のアダプタを書く。手本: Excel は枚方市、PDF は河内長野市、HTML 表は大阪市、独自の CSV は横浜市。共通の core とアプリ(src/)は変えない。変える必要が出たら、実装せずに相談する。

### 区分(kind)の決め方

| 市の区分 | kind | 注意 |
|---|---|---|
| 事前申込制の粗大ごみ | bulky | 申込セクション(電話・ネット)が出る |
| **申込制でない粗大ごみ**(シール制・通常収集) | non-burnable + `accepts_large_items: true` | bulky にすると「事前申込みが必要です」と誤案内になる(河内長野市) |
| 剪定枝など、粗大ごみとは別の申込制 | other | bulky にすると粗大ごみの申込先が出てしまう(平塚市) |
| 市が収集しないもの(処理困難物・家電リサイクル・産業廃棄物) | not-collected | 設定の `notCollectedIds` に入れる。全品目に「市では収集しません。」が付く |
| 充電式電池・パソコンなど店頭・メーカー回収 | maker-recycle | |
| 小型家電の回収ボックス | small-appliance | |
| 古布・衣類の資源回収 | paper | 横浜市の古布と同じ扱い |

### 欠かしてはいけないこと

- 市の注意点は原文のまま残す。区分名と違う市の表記は「出し方: …。」で注意文言の先頭に残す
- 1セルに2つの区分がある品目は、カードを分ける(`labelSeparator`)
- 粗大ごみの申込先は市のページのものを使う。ネット申込が無ければ `sodai_apply_url` は null
- 出典表記は市の規約の書式で、`source_license` も正確に
- 品目にない物を足さない。市のデータに無い品目(例: モバイルバッテリー)は、検索で「見つかりません」になり公式の一覧へ案内される。これで正しい

## 5. 検証

```
npm run build-data -- --municipality <slug>     # 未解決の区分ラベル 0、注意文言の欠落 0 を確認
```

- **手放し導線の付与結果を全件見る**(reuse_category が付いた品目を種類ごとに一覧にする)。誤判定は `reuse-overrides.json` で null にする。共通の判定(`enrich.ts`)は変えない(他の市の出力が変わるため)
- 家具らしい名前なのに導線が付いていない品目も一覧にする。家具の推定は kind bulky が条件なので、いす・棚・テーブルが「もやせるごみ」「金属類」などに入っている市(鹿児島市)では付かない。`reuse-overrides.json` は種類の指定もできるので、該当品目に `"furniture"` を付ける
- コミットしてから `npm run build-data -- --all` → `npm run check-data`。合格したら `git checkout -- data/` で他市の generated_at を戻す
- `npm test`、`npm run lint`、`npm run build`
- ローカルの画面(preview_start の dev)で5つ確認: ①粗大ごみの品目(申込セクションと家具の手放し導線)②市が収集しない品目(「市では収集しません。」)③2区分の品目があればそのカード ④About と詳細の出典表記 ⑤検索

## 6. PR とマージ(関所2)

- ブランチ `feat/<市名のローマ字>` → `gh pr create`。本文は日本語で「変更内容/データの確認(ライセンス・鮮度)/確認済み事項/マージ後の確認」。**URL は必ず `[表示](URL)` の形で書く**(直後に日本語を続けると、GitHub が日本語までリンクに含めて壊れる)
- `gh pr checks <番号>` で Vercel と `check`(CI)の両方が pass になるまで待つ。失敗したら直す
- 緑になってから、報告の最後にマージボタンを付ける。自分ではマージしない:

```bash
gh pr merge <番号> --merge --delete-branch
```

## 7. 本番確認(Kaz がマージしたあと)

- main の CI と Vercel が成功していること
- 本番で、自治体トップ・品目の詳細・About・検索データが 200 で返ること、既存の市が壊れていないこと
- PageSpeed Insights(モバイル)を、アプリ内ブラウザで pagespeed.web.dev を開いて計測(検索トップと詳細)。目標は Perf / A11y とも 90 以上
  - キーなしの PageSpeed API は1日の利用枠が切れていることが多い(429)
  - ブラウザの表示が隠れていると結果の画面が描画されず、スクリーンショットも撮れない。その場合は、ページ内で XMLHttpRequest を差し替えて応答を取っておき、「分析」ボタンを押し直して、応答(batchexecute の大きいもの)から `"id": "performance", … "score": 1` の形の点数を読む。応答は前半がモバイル、後半がデスクトップ
