# 公式への導線を並列で足す

決まりの本体は `docs/data-model.md` §40(導線の形・上限・載せない導線・各段の結果)。この手順書は**分担と順番**だけを書く。§40 と食い違ったら §40 が正しい。2026-11-17 Kaz 決定「市を先に、地方で4つに分ける」。

## 役割

- **統括**(このスキルを読んだセッション。1つだけ): 塊の割り振り、調べ係への依頼、塊ごとの Codex、判断待ちのまとめと Kaz への質問、apply・台帳・記録・検証・PR。**共有のファイルを書くのは統括だけ**
- **調べ係**(サブエージェント `municipality-agent`。同時に2つまで。2026-11-21 Kaz 決定: Mac が過負荷で落ちることがあるので2塊ずつ): 受け持ちの塊の市の入口探し・下書き・`check`・市ごとの記録まで。**共有のファイルとコミットには触らない**

共有のファイル(調べ係は書かない): `data/official-guides.json`・`data/guide-reviews.json`・`data/municipal-hosts.json`・`data/coverage.json`・`data/cache/catalog/fetch-log.jsonl` の手での編集・docs・記憶ファイル。

## 動かす場所

市のサイトへの接続・Codex CLI・PDF の文字の確かめ(macOS の PDFKit)は **Kaz の Mac** でしか動かない(クラウドのコンテナからは市のサイトにつながらない。2026-11-17 確認)。統括は Mac の Claude Code で動き、調べ係はそこからサブエージェントとして起こす。

- 作業フォルダは統括専用の worktree(`git worktree add .claude/worktrees/guides-<段> -b feat/official-guides-<段> origin/main`)。ほかのセッションの枝(例: 301〜400位の `feat/official-guides-4`)と書きかけには触らない
- 調べ係も同じ worktree で動く(取得のキャッシュ `work/fetch/` と予算の記録 `work/official-guides-budget/` を共有するため)。書くのは自分の塊のフォルダ `work/guides-<段>/<塊>/` だけ
- 取得はホストごとのロック(`politeFetch`。プロセスをまたぐ)で同じサイトに同時に1件・2.5秒おき。並べても同じ市に連続アクセスしない。予算は市ごとのファイルなので塊どうしでぶつからない

## 1. 塊に分ける(統括)

1. 対象: レジストリで未対応、`data/official-guides.json` に無い市。**作業中のほかの段の市を除く**(枝の `data/official-guides.json` と、その段の記録の保留の市)。2段目・201〜300位・301〜400位・5段目で保留にした市(data-model.md §40 の各段の結果に名前がある)は、Kaz が決めるまで保留のまま(対象に入れない)
2. 市(名前が「市」で終わる)を先に。町村・区は市が終わってから都道府県ごとに
3. 地方で4つの塊: A 北海道・東北 / B 関東・中部(新潟・富山・石川・福井・山梨・長野・岐阜・静岡・愛知を含む) / C 近畿(三重を含む)・中国・四国 / D 九州・沖縄。1つの塊が60市を超えたら、人口順に前半・後半に割って2回に分ける
4. 塊ごとに `work/guides-<段>/<塊>/cities.json`(slug・名前・都道府県・人口の順位)を書く

## 2. 調べ係に頼む(統括 → 調べ係、2つ同時)

重い処理は重ねない(2026-11-21 Kaz): Codex(または Gemini)は同時に1つだけ、build・テスト・check-data と Codex を重ねない。区切りごと(塊の Codex が0件・apply のあと・検証のあと)にローカルでコミットし、`work/guides-<段>/progress.md` にどこまで済んだかを1行残す

依頼の文には、塊のフォルダ、対象の市の一覧のファイル、この手順書の「3. 調べ係の手順」と「決まった型の一覧」を読むこと、共有のファイルとコミットに触らないことを書く。

## 3. 調べ係の手順

市ごとに順に:
1. 入口探し: 保存してある市のトップの本文のごみのリンク、検索エンジン。開くのは `npm run guides -- fetch <slug> <URL>`(上限に数える)。**1市 URL 3つ・接続8回**(§40)。電話のために4つ目を開かない
2. 下書き: 塊の `draft.json` に市を足す(形は `scripts/tools/official-guides.ts` の冒頭)。版・代表的な品目だけ・地区・文字のある PDF の決まりは §40
3. `npm run guides -- check work/guides-<段>/<塊>/draft.json --report work/guides-<段>/<塊>/report.json`。旗は文脈を読み、受け入れたものだけ `override` に理由を書く
4. `notes.md` に市ごとに: 開いた URL と何だったか、載せた導線と載せなかった物の理由、当てはめた型(下の一覧の番号)、電話を載せない理由
5. **一覧に無い型・迷う物は載せずに** `pending.md` に書く(市の名前・何があったか・URL・載せる案と載せない案)。ほかの導線は進めてよいが、その型の物は下書きに入れない。保留(上限で断った、など §40 の保留)は `held.md`
6. 終わったら、統括に「市の数・導線の数(種類ごと)・電話・保留・判断待ち」を返す

**apply はしない。** 共有のファイルを書くのは統括。

## 4. 決まった型の一覧(§40 と各段の Kaz 判断から)

調べ係はここに当てはめて扱いをそろえる。新しい型が Kaz に決まったら、ここと §40 の両方に足す。

| # | 型 | 扱い |
|---|---|---|
| 1 | 一覧の電池の行が市の今の告知より古い | 一覧も検索も載せず、ごみのページだけ |
| 2 | 一覧の電池の行が同じ市の今の説明と食い違う | 1 と同じ |
| 3 | 新しい版の資料が「最新はアプリで」とする一覧 | 一覧を載せず、ごみのページ(アプリの案内があればそれも) |
| 4 | 近くの市と共同で「市によって出し方が異なる」辞典 | 載せず、ごみのページだけ |
| 5 | 組合の名前の分別辞典で、市のページが案内している | 載せる |
| 6 | 地区だけの資料 | 載せない。地区を選ぶ入口があれば `area-selector` |
| 7 | 50音の一部のページ・前半だけの PDF | 索引の入口に置き換える。無ければ載せない |
| 8 | CSV・Excel・オープンデータのページ | 載せない |
| 9 | 英語だけの一覧 | 載せない |
| 10 | 許可の一覧(`data/official-guide-hosts.json`)に無い外部のサービス・委託先のサイト | 載せない(許可を足すのは Kaz の判断) |
| 11 | 公式 LINE の中の辞典を案内している市のページ | Kaz に聞く(城陽市は載せた。LINE の友だち追加のリンクは置かない) |
| 12 | 文字を抜くと欠けるが目で読める PDF | Kaz に聞く(由利本荘市は「画像の PDF」で載せた) |
| 13 | 本文が JavaScript で出て確かめられない | 保留 |
| 14 | 電話: 番号の前後に「代表」/ 本文に番号か課の名前が無い / 市の代表番号 | 電話は載せない(導線は載せてよい) |
| 15 | 切り替えの予定が分かっている | 予定日を `reviews` に |
| 16 | 古い版(2年より古い) | 版を書いて載せる(画面が知らせる) |
| 17 | 一覧・検索の電池・充電式製品・スプレー缶の扱いが、市の今の案内より欠ける(膨張・取り外せない電池・使い切り・絶縁など。食い違いでなくても) | 一覧・検索を載せない。ほかの導線が無ければ電話だけ(電話も無ければ次の段へ)。ごみのページ(top)は、冊子を配るページでない限り本文の細部まで見ない。「冊子を配るページ」は、そのページ自体に冊子・一覧表の PDF があるものだけ(別のページへのリンクの先は追わない)。2026-11-18 Kaz 判断 |
| 18 | 文字がまったく抜けない画像の PDF の一覧(型12 より文字が少ない) | 載せない(2026-11-18 Kaz 判断) |
| 19 | 50音の行ごとの PDF だけが並ぶページ(全体の PDF が無い) | 載せない(2026-11-18 Kaz 判断) |
| 20 | 組合のサイトの分別一覧(許可の一覧に無いホスト) | 載せない。許可は足さない(2026-11-18 Kaz 判断) |
| 21 | ページの版が添付の冊子の名前に付いているだけ(全体の PDF の本文に版の字が無い) | 版を付けない(2026-11-18 Kaz 判断) |
| 22 | 2年より古く、市の今の分別(プラスチックの一括回収など)より前の手引きの一覧 | 載せない(2026-11-18 Kaz 判断) |
| 23 | 市のホストの表に無い・違う市 | 調べ係は載せずに判断待ちへ。統括がまとめの apply のときに市のトップを1回確かめ、人が確かめた行として表に足す(2026-11-18 Kaz 判断) |
| 24 | 公式 LINE などの AI が答える分別案内 | 載せない。LINE の中で品目を引く案内は城陽と同じくアプリの案内で。アプリの案内は中身の電池を照らさず載せる(2026-11-17 Kaz 決定) |
| 25 | 結果を JavaScript で出す市の検索・ごみサク | 載せる(本番の同じ作りと同じ扱い。2026-11-18 Kaz 判断) |
| 26 | カレンダー・チラシなど、冊子・一覧表でない PDF だけを置くごみのページ | top に載せる(型17 の「冊子を配るページ」に当たらない。2026-11-20 Kaz 判断。古平・苫前・壮瞥)。今の年度の日程があれば、前の年度の日程が並んで残っていても載せる(2026-11-21 Kaz 判断。太地・士幌・井手)。日程の資料に日付と曜日の食い違いなどの誤りがあるページは載せない(2026-11-21 Kaz 判断。白糠) |
| 27 | 暮らし全体のページ(ごみの節があるが、住まい・税金・交通・防犯などと並ぶ) | 載せない(2026-11-20 Kaz 判断。美深・興部・比布。白糠の住まい・環境・交通も)。環境・衛生のカテゴリ(ごみのほか犬・墓地・浄化槽などが並ぶ)は1〜6段目と同じく top に載せてよい(浜中・せたな・美瑛・枝幸) |

新しい電池のお知らせと照らせない一覧は型1と同じ扱い(2026-11-17 Kaz 決定)。

## 5. 塊ごとの Codex(統括)

調べ係が終わった塊から:
1. 塊ごとの使い捨ての worktree を作る(`git worktree add .claude/worktrees/guides-<段>-<塊> -b tmp/guides-<段>-<塊> feat/official-guides-<段>`)。その中の `work` は統括の worktree の `work` へのシンボリックリンクにする(保存した本文と予算の記録を共有するため)。`node_modules` も同じくリンクする。そこで `MOTTAINAVI_OFFLINE=1 npm run guides -- apply <塊の draft.json>`(保存した本文だけで書く。新しい接続なし)→ コミット
2. `npm run codex-review -- feat/official-guides-<段> "塊<塊>の導線。notes.md と pending.md は work/guides-<段>/<塊>/ にある"`。結果を塊のフォルダに残す
3. 指摘は市のページと保存した本文で確かめ、塊の `draft.json`・`notes.md` を直して 1 からやり直す。**0件まで**
4. 枝は統括の枝に入れない(下書きが正本。0件になったら使い捨ての worktree と枝は消す。push しない)

Codex は5〜10分かかる。塊ごとに worktree が別なので、4つの塊の Codex を同時に走らせてよい。

## 6. 判断待ちを Kaz に聞く(統括)

全部の塊の `pending.md` を型ごとにまとめ、1回の質問にする(型ごとに1枚の判断のカード。推奨は「載せない」か今の型に近い扱い)。答えを待つ間も、ほかの市は進める。答えが出たら「決まった型の一覧」と §40 に書き、その市の下書きを直す。

## 7. まとめて PR(統括)

1. 統括の枝に戻り、全部の塊の `draft.json` を順に `MOTTAINAVI_OFFLINE=1 npm run guides -- apply`
2. 人口10万人未満の市の台帳の文を直す(§40「公式への導線と台帳の文」。`npm run coverage -- apply`)
3. §40 にこの段の結果の段落、roadmap の公式への導線の表に1行(手順書の変更もこの PR に含める)
4. `npm run build-data -- --all` → `npm run check-data`・テスト・lint・build → 全体の Codex(0件まで)
5. **push は1回**。PR は**約200市で1本**(塊を2〜4つ)。ほかの段の PR が先にマージされたら、main を取り込んでから PR(2回目の push はこのときだけ)
6. CI と Vercel が通ったらマージのボタンを Kaz に渡す。マージ後に本番確認(スマホ幅・日英・リンクを数件)と記録
