# data-model.md — データモデル設計書

バージョン: v0.1 (2026-07-04)

---

## 1. 設計方針

- **3層構造**: 「品目」「自治体別ルール」「手放し導線」を分離し、将来の自治体追加・多言語追加に耐える
- MVPはDB不使用。**ビルド時に読み込む静的JSON**として保持(SSG)
- すべてのデータファイルは `data/` ディレクトリに配置し、パイプラインスクリプトで生成

```
data/
├── municipalities.json        # 自治体マスタ
├── items/
│   └── osaka-city.json        # 品目+ルール(大阪市)※パイプライン生成
├── reuse-options.json         # 手放し導線マスタ(手動管理)
├── i18n/
│   ├── ui.ja.json             # UI文言(日本語)
│   ├── ui.en.json             # UI文言(英語)
│   └── items.en.json          # 品目名英訳(主要300件)※半自動生成
└── categories.json            # 収集区分マスタ(色・アイコン・多言語名)
```

### 2.3 items/osaka-city.json(品目+ルール)

パイプラインが市の一覧表HTMLから生成。1レコード=1品目行。

```json
{
  "municipality_id": "osaka-city",
  "generated_at": "2026-07-05T09:00:00+09:00",
  "source_url": "https://www.city.osaka.lg.jp/kankyo/page/0000201907.html",
  "item_count": 1234,
  "items": [
    {
      "id": "osk-0001",
      "name_ja": "アイロン",
      "name_kana": "あいろん",
      "aliases": ["スチームアイロン", "iron"],
      "dispositions": [
        {
          "category_id": "futsu",
          "note_ja": "最大の辺または径が30cmを超えるものは粗大ごみ収集受付センターへお申込みください。",
          "official_link": "https://www.city.osaka.lg.jp/kankyo/page/0000009139.html"
        }
      ],
      "sodai_fee_yen": null,
      "reuse_category": "small-appliance",
      "name_en": "Iron (clothes iron)"
    }
  ]
}
```

フィールド仕様:

| フィールド | 型 | 生成方法 |
|---|---|---|
| id | string | パイプラインで連番付与(`osk-` + 4桁) |
| name_ja | string | HTML「品目(素材など)」列そのまま |
| name_kana | string | パイプラインでかな変換(kuromoji等)。検索正規化用 |
| aliases | string[] | 別名辞書(手動管理 `data/aliases.common.json` + 市の `aliases.json`)から、品目名が語と一致または語で終わるときだけ付ける(§2.5・§36) |
| dispositions | array | 同一品目の複数行を1品目に集約。区分・ポイント・公式リンク |
| sodai_fee_yen | number/null | ポイント欄の「処理手数料 1台400円」等を正規表現抽出 |
| reuse_category | string/null | ヒューリスティック(§4)+手動上書きで付与 |
| name_en | string/null | 主要300品目のみ。i18n/items.en.json からマージ |

### 2.5 aliases.json(別名辞書・手動管理)

```json
{
  "ペットボトル": ["PET", "ペット", "plastic bottle"],
  "スマートフォン": ["スマホ", "携帯", "iPhone", "Android"],
  "テレビ": ["TV", "液晶テレビ"]
}
```

**別名の付け方(2026-10-23 に変更。`scripts/core/aliases.ts` の `buildItemAliases`、詳細は §36)**: 辞書の語が品目名に含まれていれば付ける、ではなく、次のときだけ付ける。
- 品目名のカッコ・※以降を注記として外し、ハイフン・空白で区間に、「・」「、」で部分に分ける。「本体」「類」「等」「など」「一式」「全般」と末尾の数字も外して比べる
- 部分が**語と一致** → 語の別名を全部付ける。ただし (a) 1文字の語(油・本・靴・鏡・傘・缶)は注記のない完全一致のときだけ(油（食用以外）・靴（スキー靴）・鏡（手鏡）に食用油・スニーカー・姿見を付けない)。(b) ストーブ・電球は、注記や空白のあとに限定がある品目(ストーブ（電気）・ストーブ　電気・ガス)には、限定にその種類の言葉(石油。灯油も同じ)があり否定されていないときだけ兄弟の別名(石油ストーブ・LED電球)を付ける。(c) 「自転車・バイクのアクセサリー」「DVD・ブルーレイディスクプレーヤー」のように最後の区間が「〜の〜」「〜用」や機器(プレーヤー・ドライブ・レコーダー・デッキ)なら、前の部分は一致に使わない。(d) 「椅子（いす）」「バッグ（かばん）」のように、カッコの中の語の別名が外の部分なら同義語として一致とみなす。用途のカッコ(液晶ディスプレイ(パソコン))は使わない
- 部分が**語で終わる**(下位の種類。ノートパソコン・ベビーベッド・電気ストーブ。かなはそろえず比べる。スパイスはいすで終わらない) → 語を**含まない**別名だけ付ける(PC・laptop・bed・ヒーターは付くが、「石油ストーブ」「LED電球」のような兄弟の別名は付かない)。ただし品目名自身が含む別名なら付ける(電子ピアノに電子ピアノ。付けないと並び順で語そのもの(ピアノ)の品目が先頭に出る)
- 語のあとに**許可リスト**(`TAIL_ALLOW`)の言葉が続く(タブレット端末・DVDディスク・新聞紙・蛍光灯管・段ボール箱・携帯ゲーム機器) → 上と同じ
- 語で終わっても別の物は**遮断リスト**(`TAIL_BLOCK`: 座布団・原動機付自転車・エアロバイク・水上バイク・タイプライター・LED蛍光管・ラタンキャリーバッグなど)で外す。ポットは前の言葉が合うとき(電気・湯沸かし・ジャー…)だけ(`TAIL_PREFIX`)。クーラー・ふとん(ひらがな)は名前が一致するときだけ(`EXACT_ONLY`)。エレキギターにアコギは付けない(`TAIL_DROP`)
- 市の `aliases.json` は共通辞書の語を上書きし(空の `[]` で別名を消せる)、品目名そのもの(例: `"電池（筒型）アルカリ・マンガン"`)をキーにして個別の品目に別名を付けることもできる(カッコの中に種類を並べた総称の品目は、この方法で補う)
- 比較は検索と同じ正規化(NFKC・小文字・かな・長音)。ただし「語で終わる」だけはかなをそろえない
- **言い換え辞書**: 1字違いでない言い換え・表記ゆれは、データにある側の語をキーにして、利用者が引く語を別名にする(蛍光管→蛍光灯、除湿器⇔除湿機、充電式電池・充電電池・二次電池→充電池、アルカリ電池・マンガン電池→乾電池、オートバイ⇔バイク、釣竿・釣りざお⇔釣り竿、ダンボール→段ボール、携帯電話→ガラケー・携帯、スマートホン→スマホ、スーツケース⇔キャリーバッグ、雑紙⇔雑がみ、ガラスくず→割れたガラス、ズック→スニーカー、使い捨てライター→百円ライター、ふとん→布団、クーラー→エアコン、CD/DVDのプレーヤー・デッキ・レコーダー→機器の別名、ほか)。足すときも上の条件が働くので、別の区分の品目には付かない
- **言い換えにしなかったもの(別の区分へ誘導するため)**: 注射針⇔注射器(座間市は針と筒で案内が割れる。八王子市は針は収集せず筒は可燃)、紙パック→牛乳パック(酒の紙パックは別区分)、買い物袋→レジ袋(買い物袋は燃やすごみ)、剪定ごみ→剪定枝(落ち葉と大型ごみの枝は別区分。枝だけの品目がある東大阪市・高松市・福岡市・山鹿市・広島市は市の辞書で)、携帯電話→スマホ(スマートフォンの品目と区分が違う市がある。携帯電話しか品目が無い11市は市の辞書で)
- 影響の確認は `npm run alias-impact`(別名の総数と「別名で見つからなくなる組」)と `npm run search-diff`(代表の語の検索結果の前後比較)、1市・数語は `npx tsx scripts/tools/search-probe.ts <slug> <語>...`

## 3. データパイプライン仕様(scripts/build-data.ts)

1. **fetch**: 大阪市「品目別収集区分一覧表」ページのHTML取得(ローカルにキャッシュ保存。再実行時はキャッシュ優先オプション)
2. **parse**: テーブル行を抽出 → { name_ja, category_label, note, links } の生配列に
   - rowspanで品目名が空の行(複数区分)は直前の品目に集約
   - 区分ラベル→category_id のマッピング表で正規化。未知ラベルは警告出力
3. **enrich**:
   - name_kana 生成(形態素解析 or 簡易かな変換)
   - sodai_fee_yen 抽出(正規表現: `処理手数料.*?([\d,]+)円`)
   - reuse_category 付与(§4のルール)
   - aliases.json / items.en.json をマージ
4. **validate**: 件数チェック(±10%超の変動で警告)、必須フィールド欠損チェック、category_id未解決の一覧出力
5. **emit**: `data/items/osaka-city.json` 書き出し + 統計サマリをコンソール表示

## 4. reuse_category 付与ヒューリスティック

| 条件(品目名/区分) | reuse_category |
|---|---|
| 名前に「衣」「服」「ウェア」/ 区分=古紙・衣類(衣類系) | clothing |
| 区分に kogata-kaden 系を含む | small-appliance |
| 区分 kind=bulky(または `accepts_large_items` の区分)かつ 名前に「いす/棚/机/タンス/ベッド/ソファ」等(アイス・スライス・コンロ類は除外) | furniture |
| 名前に「本/書/雑誌/CD/DVD/レコード」 | books-media |
| 名前に「おもちゃ/ベビー/絵本/乳母車」 | toys-baby |
| 名前に「ギター/ピアノ/オルガン/楽器」 | instruments |
| ポイント欄に「リターナブル/購入店・販売店へ返却」 | returnable |
| 上記以外 | null(手放し導線セクション非表示) |

自動付与の結果は `data/reuse-overrides.json` で個別上書き可能にする。

## 5. 多言語データ方針

- UI文言: `ui.ja.json` / `ui.en.json` の完全対訳(キーは共通)
- 品目名英訳: 検索頻度が高そうな300品目を `items.en.json` に整備(Claude Codeで下訳生成 → Kazがレビュー)。英訳が無い品目は日本語名表示+区分・注意点は英語UI文言でフォロー
- 検索は日英どちらの入力でもヒットするよう、Fuse.jsのkeysに name_ja / name_kana / aliases / name_en を含める

## 6. 設計方針の変更点

| 論点 | v0.1(大阪市のみ) | v0.2(全国) |
|---|---|---|
| 収集区分 | 全自治体共通の enum 12種 | 自治体ごとに定義+アプリ共通の `kind`(意味種別)を必須付与 |
| 品目ID | `osk-` + パース順の連番 | prefix は自治体属性。`id-map.json` で品目名↔IDを固定 |
| データ配置 | `data/items/<muni>.json` をバンドルに同梱 | `data/municipalities/<muni>/` に原本、`public/data/<muni>/` に配信用を導出 |
| 手放し導線 | 全品目共通 | `municipality_id` を持つ選択肢は該当自治体でのみ表示 |
| UI文言 | 「大阪市」をベタ書き | `{municipality}` プレースホルダ |

## 8. municipalities.json(全国レジストリ)

全国1,741市区町村(市町村1,718+特別区23)を1ファイルで持つ。総務省「全国地方公共団体コード」から
`scripts/build-registry.ts` で一度生成し、以後は `status` と `slug` を手で保守する。`official_url` は、対応自治体は手で入れ、未対応の市区町村は `npm run coverage -- official-url` で入れる(§30)。

```json
[
  {
    "slug": "osaka-city",
    "lg_code": "271004",
    "pref": "大阪府",
    "name_ja": "大阪市",
    "name_en": "Osaka City",
    "status": "supported",
    "official_url": "https://www.city.osaka.lg.jp/kurashi/category/3016-1-2-0-0-0-0-0-0-0.html"
  },
  {
    "slug": "osaka-sakai-city",
    "lg_code": "271403",
    "pref": "大阪府",
    "name_ja": "堺市",
    "name_en": "Sakai City",
    "status": "unsupported",
    "official_url": "https://manage.delight-system.com/threeR/web/bunbetsu?menu=bunbetsu&jichitaiId=sakaishi&lang=ja"
  }
]
```

| フィールド | 仕様 |
|---|---|
| slug | URL に出る自治体ID。`^[a-z0-9-]+$`。レジストリ内で一意(zod + 重複検査で保証) |
| lg_code | 全国地方公共団体コード6桁。オープンデータ連携の主キー |
| status | `supported`(品目データあり) / `unsupported`(未対応) |
| official_url | http(s) の URL だけ(`javascript:` などは検査で拒否)。対応自治体は市のごみのページ。未対応の市区町村は、判明していれば入れる(堺市は市の分別辞典、ほかは確かめた市のトップページ。§30)。無ければ null |
| (未対応の理由) | レジストリには持たない。仕分けの台帳 `data/coverage.json`(§30) |

**同名自治体の slug 衝突**: 府中市(東京都/広島県)、伊達市(北海道/福島県)など。
衝突する場合のみ都道府県を前置する(`tokyo-fuchu-city` / `hiroshima-fuchu-city`)。
衝突しない自治体に都道府県は付けない(既存の `osaka-city` を変えないため)。

## 10. categories.json の自治体別化と kind

区分IDは自治体ごとの自由文字列(`^[a-z0-9-]+$`)にし、アプリ共通の `kind` を必須にする。
**UIロジックとパイプラインは区分IDではなく kind で判定する**。

kind の enum(アプリ側固定):

| kind | 意味 | アプリ側の挙動 |
|---|---|---|
| burnable | 可燃・普通ごみ | — |
| non-burnable | 不燃ごみ | — |
| recyclable | 資源(缶・びん・PET) | — |
| plastic | プラスチック資源 | — |
| paper | 古紙・紙類(衣類含む場合あり) | — |
| bulky | 粗大ごみ | 詳細ページに申込セクション(手数料・申込URL・電話)を表示 |
| small-appliance | 小型家電・PC等のリサイクル回収 | reuse_category を `small-appliance` と推定 |
| maker-recycle | メーカー・販売店による回収(パソコンリサイクル等) | small-appliance の推定をしない(市の小型家電回収と別制度) |
| hazardous | 電池・スプレー缶など危険物 | — |
| drop-off | 拠点回収・集団回収 | — |
| not-collected | 市が収集しない | 注意文言の欠落をパイプラインが警告(誤案内リスク最大) |
| other | 上記に当てはまらない | — |

色とアイコンは kind ごとの既定値をコード側(`src/lib/category-kind.ts`。クライアントでも読むため zod 非依存)に持ち、
自治体の categories.json で任意に上書きできる。既定値は現行の大阪市の配色をそのまま採用するため、
Phase A で見た目は変わらない。

## 11. 品目IDの安定化(id-map.json)

**v0.1 の不具合**: パース順の連番で採番していたため、市が一覧表に1行追加すると
以降の全IDがずれ、公開済みURLが別の品目を指す(誤案内)。Phase A で修正する。

```json
{
  "prefix": "osk",
  "next_seq": 1057,
  "map": { "アイロン": "osk-0001", "アイスノン": "osk-0002" }
}
```

- パイプラインは品目名で `map` を引き、既存品目は同じIDを再利用する
- 未登録の品目のみ `next_seq` から採番し、`map` に追記する
- 削除された品目のエントリは残す(IDの再利用を防ぐ)。再登場時に同じIDへ戻る
- 既存の1,056件は現行 items.json の値でそのまま初期化するため、公開中のURLは変わらない
- スキーマは `^[a-z0-9]{2,8}-\d{4}$`(prefix は自治体属性)

## 19. 河内長野市(Phase C-3)で確定した事項(2026-09-23)

- **出典**: 市の「家庭用ごみの分別辞典(50音順)」PDF(R8年作成、CC BY 4.0、1,089品目)。出典表記は市の指定どおり「このデータベースは、以下の著作物を改変して利用しています。家庭用ごみの分別辞典、河内長野市」
- **PDF の取り出し**: Node の pdfjs-dist では表の行が崩れるため、pypdf で取り出したテキストを `data/cache/kawachinagano-city.txt` に置き、アダプタはそれを切り出す(`scripts/adapters/kawachinagano-city/extract_text.py`。PDF 更新時のみ手動実行)。`source_type` に `opendata-pdf` を追加

## 22. 取得元の状態 source.json(2026-10-02)

`data/municipalities/<slug>/source.json` に、データの取得元を置く(スキーマは `scripts/core/source.ts`)。アプリは読まない(パイプラインと見張りだけが使う)。

```json
{
  "file_url": "https://www.city.example.lg.jp/common/200203599.csv",
  "fingerprint": "https://www.city.example.lg.jp/common/200203599.csv | ごみの分別方法一覧（CSV:66KB） | 最終更新日：令和8年2月1日"
}
```

- `file_url`: データファイル(大阪市は品目表のページ)の URL。アダプタの `fetchSource` はここから取得する。市が新しい URL でファイルを出したら、データ更新の見張り(tech-stack.md §17)が書き換える
- `fingerprint`: 最後に確認したときの目印。見張りは、いまの目印がこれと違えば更新とみなす。空文字は「まだ記録していない」(URL が同じなら、取り直さずに記録だけする)
- `municipality.json` の `source_url`(出典として表示する掲載ページ)とは別物

## 25. 品目名の英訳の追加(沖縄市で試行、2026-10-03)

一次ソースに英語の品目名は無い。全国共通の辞書(`data/i18n/items.en.json`、299件)は品目名の完全一致でしか当たらず、大阪市以外ではほとんど付かない(全9市で 6.1%)。全市へ広げる前に、沖縄市で試した。

- **置き場所の決まり(2026-10-03、全市へ広げるにあたって)**: ふつうの訳は共通辞書 `data/i18n/items.en.json` へ入れる(同じ品目名のある他の市にも付く。同じ品目名でも市によって区分は違うが、物が同じなら訳は共通でよい)。区分や注意点から意味を補った訳と、意味が確定できない品目の訳だけ、自治体の辞書に入れる。試行の692件のうち680件を共通辞書へ移し、12件(油・木・キーパー・コイン・灯油タンク・バッテリー・ハンディースペンサー・保冷庫・かま・バット・ガス台・やすり)を沖縄市の辞書に残した
- **表記ゆれの吸収**: 英訳は、品目名を NFKC と空白除去でそろえて引く(`itemNameKey`。「植木鉢(陶器製)」と「植木鉢（陶器製）」は同じ品目名)。同じ辞書の中では、そのまま一致するキーを優先する
- **作り方**: Claude が品目ごとに区分と注意点を見て訳す → 機械的な点検(キーが実在の品目名か、空でないか、ASCII か、抜けが無いか)→ 別のサブエージェントが全件を読み直す(27件を修正)→ Kaz が「要確認」の品目と抜き取りを見る
- **訳の決まり**
  1. 品目名だけを訳す。出し方・区分の情報は足さない
  2. 括弧内の条件(大きさ・素材・「PCBなし」など)は落とさない。区分の判断に関わるため
  3. 書き方は共通辞書に合わせる: 文頭だけ大文字、補足は括弧、言い換えは ` / `(例 `Iron (clothes iron)`)。文字は ASCII
  4. 日本・沖縄特有のものはローマ字と説明を並べる。英語に定着した名があれば英語を先(`Teapot (kyusu)`)、無ければローマ字を先(`Kotatsu (heated table)`)

## 30. 仕分けの台帳(data/coverage.json)と未対応の市区町村の公式サイト(2026-10-15)

月末(2026-10-31)までに全1,741市区町村を仕分ける(Kaz の決定、2026-10-14)ための台帳。未対応の市区町村ごとに「なぜ未対応か」を、状態・確かめた日・根拠つきで持つ。形と検査は `src/lib/coverage.ts`(画面で使う定数と型は zod を使わない `src/lib/coverage-display.ts`)。

- **別のファイルにした理由**: `scripts/build-registry.ts` はレジストリの決まった項目以外を消し、形が1件でも合わないと手で入れた値まで全部初期化する。台帳を別にすれば、作り直しても台帳は残る
- **未対応の市区町村だけを持つ**。対応済みかどうかはレジストリの `status` が正(二重に持たない)。**台帳の slug の集まり = レジストリで未対応の slug の集まり**(過不足ゼロ)を、共通の検査関数 `assertCoverageMatchesRegistry` で確かめる。使う場所: アプリの読み込み(`src/lib/data.ts`。開発サーバーでも効く)・ビルド前の準備(`scripts/build-public-data.ts`)・台帳の道具・テスト。自治体を追加したら、レジストリを `supported` にするのと同じコミットで台帳から消す
- **書き換えは道具で**(`npm run coverage -- set` / `apply` / `sync` / `summary`。`scripts/tools/coverage.ts`)。書く前にレジストリと台帳の全体を検査し、通らなければ書かない。キーはレジストリの順(全国地方公共団体コード順)、項目は決まった順で書く(同じ内容なら同じファイルになる)

1件の形:

| 項目 | 仕様 |
|---|---|
| status | `available`(入力できる)/ `candidate`(確認中)/ `hold`(保留)/ `license`(使える条件を確かめられない)/ `no-data`(見つからない)/ `unsurveyed`(未調査)。月末の最終の分類は available / hold / license / no-data(+対応済み)。candidate と unsurveyed は途中の状態。available は「抜き取りの照合で大きな食い違いが無く、Kaz が入れると決めた」(全件の照合は入力のとき。そこで食い違えば hold に戻す) |
| checked_at | その分類を最後に確かめた日(日本時間)。実在する日付で、未来は不可。**記録に正確な日付が無ければ作らない**(その市は unsurveyed のまま) |
| detail_ja / detail_en | その市だけの事情(画面に出す)。両方そろえる |
| evidence | 判断に使った資料 `{label, url?}`(データ・規約・市の現行の案内・roadmap の記録)。unsurveyed 以外は1件以上 |
| searched | no-data のとき、探した場所 `{label, url?}`。no-data では1件以上 |
| note | 内部向けのメモ |

- **画面に出すのは status・checked_at・detail_ja・detail_en だけ**(`toPublicCoverage`)。evidence・searched・note は、未対応ページ(ブラウザで動く部品)に渡さない(渡すと、表示しなくてもページの中身に入るため)
- **license と no-data の分け方**: license は、再利用できそうな形の品目一覧(CSV・HTML の表・Excel など)は見つかったが、このアプリで使ってよい条件を確かめられない(表記が無い・転載禁止)。no-data は、オープンデータとしての品目一覧が見つからない(市のサイトの検索システム・PDF の冊子・アプリにしか無い場合を含む)
- **hold の中身**: 公開データが市の現行の案内と食い違っていた(寝屋川市・泉大津市など)か、制度の変更が反映されていない(名古屋市・宮崎市など)か、古いファイルしか無く合っているかを確かめられない(神戸市)
- **最初の台帳(2026-10-15)**: 記録に日付と根拠がある60件(入力できる2・確認中10・保留9・使える条件を確かめられない6・見つからない33)。根拠は roadmap の Phase C と、2026-10-08 の候補の一括調査。残りの1,668件は未調査。大阪府の「なし」の37市町村(2026-09-23 の棚卸し)は、堺市(license)と準候補4市町(吹田市・岸和田市・太子町・高石市。表はあるがライセンスの表記なし → license)を除く32市町村を no-data にした
- **対応済みの市の公開を止めるとき**(データが古くなったなど)は、台帳の hold とは別の手順: レジストリを unsupported に戻し、アダプタの登録を外し、台帳に hold で理由を書く(update-municipality-data の手順書)
- **保留の市の見直し**: 週1回の見張り(アダプタを登録した市が対象)の外なので、第2段の総当たりと、その後は月1回の総当たりで見直す

### データカタログの総当たり(第2段、2026-10-16〜)

未調査の市区町村を、国内のデータカタログをプログラムで総当たりして仕分ける。判定は `scripts/core/catalog.ts`(ネットワークに出ない純粋な関数)、手順は `npm run sweep`(`scripts/tools/catalog-sweep.ts`)、取得は `scripts/core/polite-fetch.ts`。

- **探し先の一覧は `data/catalogs.json`**: CKAN(BODIK・東京都・県や市のカタログ)、CKAN 互換の API(dataeye の `/ckan_api`、SHIRASAGI の `/api/package_search`)、search.ckan.jp(国内の CKAN の横断検索)、e-Gov データポータル、API の無いカタログ(`kind: "manual"`。人がサイト内検索で確かめた日と方法を書く)。県ごとの棚卸しの結果もここに残す。**県のカタログの棚卸しが済んでいない県の市は「見つからない」にしない**(`prefs` か `coversPrefCatalogs` にその県がある探し先が要る)
- **取得の決まり**(`polite-fetch.ts`。総当たり・抜き取り照合のエージェント・入力の工程で共通): 1つの URL は1回だけ取得してキャッシュする(本体は `work/fetch/`、記録は `data/cache/catalog/fetch-log.jsonl`)。ホストごとに同時1件・2.5秒以上あける(別のプロセスともロックで調整)。取得は curl(証明書の確認は外さない)。失敗したときの再試行は1回だけで、取り直しは URL を指定して1件ずつ。エージェントは `npm run fetch -- <URL>` で使う
- **語の検索は取りこぼす**: BODIK などの日本語の検索は語によって漏れる(2026-10-16 の棚卸し)。q を複数(ごみ・ゴミ・分別・資源物・粗大、BODIK と東京都はデータセットの名前 garbage・gomi・bunbetsu なども)で問い合わせて合わせる
- **機械が出すのは提案**。台帳には `npm run coverage -- apply-proposal` で書く。提案には市ごとに「書く前の状態」があり、いまの台帳と違えば何も書かずに止める

### 未対応の市区町村の公式サイト(official_url)

- **Wikidata は候補にとどめる**。Wikidata(CC0)の「公式サイト」(P856)を、全国地方公共団体コード(P429)で突き合わせて候補を集める(問い合わせ1回、`data/cache/wikidata-official-sites.json`)。Wikidata には古い URL(非推奨・終了日つき)や外国語のページも入っているので、そのままは使わない
- 候補の選び方: 非推奨・終了日つき・http(s) 以外を除く。トップページ(パスが / や /index.html)の候補があれば、それだけにする
- **1件ずつ確かめる**(`scripts/core/official-url.ts`): 候補に1回だけ接続し(同時に4件、どのサイトにも1回だけ。確かめ済みの候補には再接続しない。結果は `data/cache/official-url-check.json`)、①応答が 200 ②行き先のホスト名が自治体のサイトらしい(`.lg.jp`、city / town / vill / village / ku のラベルがある `.jp`、または名前のローマ字を含む `.jp`。ローマ字の書き方のゆれ mombetsu / monbetsu は同じとみなす。ホスト名をラベルに分けて判定し、部分一致にしない)③ページの題名に自治体の名前がある(同じ名前の自治体がほかにある場合は都道府県名も)。通った候補の行き先が1つに決まるときだけ入れる。その市の候補を全部確かめ終わっていることも条件にする(`--limit` で途中までにした市は、行き先が複数かどうかが分からないので入れない)
- **接続は curl で行う**(`-sL`、転送は5回まで、20秒で打ち切り。証明書の確認は外さない)。自治体のサイトには、証明書の中間証明書を送っていないもの(証明書の連鎖が不完全)が多く、Node の fetch は `UNABLE_TO_VERIFY_LEAF_SIGNATURE` で失敗する。macOS の curl はシステムの仕組みで連鎖を補って確かめるので、ブラウザと同じ結果になる(2026-10-15、Node では 1,274件、curl で 1,658件が通った)
- **古いドメインから .lg.jp の候補を作る**: Wikidata の候補(`www.city.kuji.iwate.jp` など)に接続できない・200 でないときは、`www.city.kuji.lg.jp` の形も候補にして同じ確かめを通す(`lgJpVariant`)。作った URL もそのままは入れない
- **2026-10-15 の結果**: 未対応の1,727件のうち 1,658件に入れた(`.lg.jp` 725・city / town などのラベル 853・名前のローマ字 80)。同じ URL が2つの自治体に入ったものは0件。名前のローマ字だけで通った80件は題名を1件ずつ、ほかから無作為の20件も目で確かめた。入れなかった69件の内訳は、`.com` などのホスト名・題名に名前が無い(または同じ名前の自治体があるのに都道府県名が無い)・接続できない・行き先が複数(新宿区)。もう一度実行しても追加0件で、ファイルは変わらないことを確かめた
- **すでに入っている URL は上書きしない**(対応済みの市・堺市)。通らなかった市は null のまま(画面は「お住まいの自治体の公式サイトでご確認ください」)
