## 進め方の原則

- 1フェーズ = Claude Code の1セッション目安。**プランモードで計画→承認→実装→動作確認→コミット**を各フェーズで回す
- 各フェーズの「完了条件」を満たしてから次へ。満たせない場合はスコープを削る(機能を削っても完了条件は守る)
- 詰まったら15分ルール: 15分解決しなければ回避策(モック・手動データ・機能削減)に切替

## Phase B: 2つ目の自治体投入(設計検証)★本当の分水嶺 ✅ 2026-09-23 完了・本番反映(横浜市)

候補は堺市または横浜市だったが、**横浜市**にした(Kaz 承認 2026-09-23)。
堺市は品目一覧が市サイトのPDFと外部業者のシステムにしかなく、市サイトの著作権ページが「無断で複製・転用することはできません」。
CC BY 4.0 のオープンデータ利用規約はカタログ掲載データ(収集曜日・処理量統計)にしか及ばない。
「ライセンス不明・不許可のデータは投入しない」原則により見送り。市に許諾を申請すれば投入できる可能性はある。

やること:
- 選んだ自治体のアダプタを1本書く(`scripts/adapters/<slug>/`)
- その自治体の `categories.json`(大阪市に無い区分。不燃ごみなど)を定義
- 自治体固有の手放し導線を `municipality_id` 付きで追加
- `build-data --all` の実装
- 設計の破綻箇所を洗い出して Phase A の構造を修正する

完了条件:
- [x] **アプリ側のコード変更なし**(データとアダプタの追加だけ)で2自治体目が動く — ほぼ成立。唯一の例外は注意文言の改行表示(`whitespace-pre-line` 1クラス。大阪市の文言に改行が無く表面化していなかった)
- [x] 2自治体でスポットチェック各10品目が公式表と一致(横浜市11品目を CSV 原文と突き合わせ)
- [x] 自治体を切り替えても前の自治体のデータが混ざらない
- [x] 手放し導線に他自治体の拠点回収が出ない(大阪市の拠点回収は大阪市だけ、横浜市の回収ボックスは横浜市だけ)

Phase A の構造が破綻していた場合は、ここで直す。Phase C に進む前に必ず解決する。

**本番確認(2026-09-23)**: PageSpeed Insights(モバイル) 横浜市 検索トップ Perf100/A11y100、詳細 Perf100/A11y100。大阪市の表示・データは変更なし。堺市の未対応ページは市公式の分別辞典(さんあ〜る)へ案内。

**検証結果(2026-09-23)**: 構造は破綻しなかった。判明した課題は次のとおり(Phase C で扱う)。
- 手放し導線の推定(enrich.ts)は大阪市の表記に合わせた正規表現で、横浜市では付与率 8.8%(大阪市 18.8%)。「販売店または缶・びん・ペットボトル」をリターナブルと判定できない等
- 品目名英訳(items.en.json)は品目名キーのため横浜市では 44/3,413 件しか当たらない。表記ゆれを吸収する仕組みか、自治体別の英訳が必要
- 粗大ごみ手数料は CSV に無く、横浜市は動的ページのため未取得(申込先とネット申込の導線は出る)
- 検索インデックスは3,413件で gzip 77KB(大阪市 34KB)。予算(300KB)内だが、1万品目級の自治体では分割を検討

## 優先順位(迷ったときの判断基準)

1. **誤案内ゼロ** — 対応自治体数より優先する。怪しいデータは投入しない
2. **月額0円** — サーバ・DBを導入しない。無料枠に依存する仕組みも避ける
3. **1人で維持できること** — 自動化できない運用は増やさない
4. 対応自治体数

削らないもの: 出典表記、非公式ツールの明示、注意文言の全文保持、未対応自治体の正直な表示。
